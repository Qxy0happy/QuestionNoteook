**Blocked by:** 05（入库与题库列表）

**Status:** ready-for-human —— 代码已落地，`go test` / `svelte-check` / 构建全过；剩下的是真机上走一遍

- [x] 能从错题详情触发补拍答案图
- [x] 答案图复用与题图完全相同的采集与落盘路径
- [x] 缺答案的错题在列表与复习界面上有标记
      —— 两处共用 `AnswerBadge`：列表行里是它，复习界面在**自评之前**就显示（`Review.svelte`

## Comments

### 补拍怎么走完一趟

详情页新增一行动作（「补拍答案图」/「重拍答案图」+「标签」）。按下之后由 `App.svelte`
记下**是哪道题**并把页面滑到取景页 —— 题库页不知道该怎么做这件事，它只把题交上去。

取景页在补拍态下走的是**同一条**路径：`confirm()` 里判定当前是补拍就把 `AttachAnswer(id, …)`
而不是 `Capture(…)`，两者都落在同一对「拉正 + 按内容 hash 落盘」上，只是补拍多一步
`SetAnswerHash`。**题图与答案图共用一张去重表**，所以同一张图完全可能既是 A 的题图、
又是 B 的答案图（ADR-0004）。

### 状态泄漏：一个只有走完整流程才看得见的坑

`Capture` 只在用户按「完成」时回调，**取消路径不存在** —— 而 Cancel 的方式就是横向滑走。
不在别处清掉的话那道题的 ID 会一直挂着，几十秒后对着另一道题按下快门，答案图就**静默挂到了
之前那道题上**。

处置在 `App.svelte`：补拍态只在取景页停稳的时候算数（滚动停了之后再判当前在哪一页）。
判据放在「停稳后」而不是 `scroll` 事件里，是因为切页用的是平滑滚动，起手那几帧还在题库页上，
边滚边判会把刚设上的补拍态立刻抹掉。

### 换下来的旧答案图会被回收

`AttachAnswer` 返回后 Go 侧会问一句「这个旧 hash 还有别的错题引用吗」，没有才删文件。
重拍过的那张就是在这里才算真的落地 —— 前端不需要知道文件的事。

### 题库详情页也能看答案图了（2026-09-16 用户提的）

用户原话：「允许查看答案图，这里只是拍摄答案图，拍完了只在复习时能看。」
在那之前详情页只能**补拍**，看不到它 —— 答案图只在复习评完之后才露出来，那是个真的缺口。

- 入口是动作行里一个按钮，文案在「看答案图」/「收起答案图」之间切；**只在有答案图时才渲染**
  （判断走 `answer.ts` 的 `hasAnswer` 一处，不在组件里再写一遍 `AnswerHash !== ''`）。
- **默认不摊开**：它是对答案用的，不该一进详情就糊在脸上。收起**不丢**已取到的图（内存里缓存着）。
- 摊开的位置：题图**下面**，两块各占一半高度，中间一条分隔线 —— 对着看。
- 走已有的 `Library.AnswerImage(hash)`（**不是**新绑定的方法），与题图**共用同一份** `hash → data URL`
  缓存（键就是内容 hash，同 hash 即同一张图）。
- 加载中 / 取不到（文件被清理）与题图**同一套话术**；异步回来时照旧校验 `opened?.ID`，
  中间换题或返回就不贴上去。
