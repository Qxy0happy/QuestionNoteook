# 04: 手选框 → 透视拉正 → 落盘

**What to build:** 快门之后底图铺满屏幕，上面压着一个居中的、**可变边长**的矩形选框，可以拖动。确认后应用把选区内那道题**透视拉正**，显示成卡片图，并把文件按**内容 hash** 落在沙箱里。

这是采集的核心：确认那一刻定稿，原图不再保留。

**Blocked by:** 03（取景与快门）

**Status:** ready-for-agent

- [ ] 选框初始居中、默认尺寸；拖角改尺寸、拖内部平移
- [ ] 确认后调用 Go 侧，传入原图与**四个角点**
- [ ] Go 返回拉正后的卡片图，界面上显示出来
- [ ] 卡片图按内容 hash 命名，落在应用私有目录
- [ ] 同一张图导入两次只产生一个文件
- [ ] 重拍与旋转可用
- [ ] 确认之后原图不再保留（这是刻意的，见 ADR-0007）
- [ ] Go 侧有 fixture 测试：喂一张**程序生成**的、带已知畸变的图，断言拉正后预期位置有预期像素

## Comments

**2026-09-16 · Go 侧完成，前端（手选框）未做**

`internal/capture/` 已实现并通过测试：透视拉正（Heckbert 闭式解 + 反向映射 + 预乘 alpha 双线性）、按内容 hash 落盘（原子改名、并发安全、hash 取像素而非编码字节）。

测试的 fixture 程序生成，生成路径刻意与被测代码走不同方法（DLT + 高斯消元），并拿一个故意写错的「只裁包围盒」实现验明正身：25 个格心里 12 个对不上 —— 证明这条 fixture 确实分辨得出透视拉正与裁剪之别。

**仍未做**：票据的前端那半 —— 手选框 UI、重拍/确认/旋转、以及把角点交给 `capture.Rectify`。服务已接线（`capture.Service`），绑定已生成，但**整条链一次都没端到端走过**。

## Comments

**2026-09-16 · 前端那半也已完成（更正本节上方那条留言）**

手选框与确认入库都已实现（提交 ad0d6c3），本节早先写的「前端（手选框）未做」是过期的。

- `frontend/src/CropBox.svelte`（新建）：选框用**归一化到帧**的坐标（0..1），角柄改尺寸、框内平移；`apply()` 是纯函数（从「起始选框 + 位移」算新框，不做增量累加 —— 增量会被每次舍入咬掉，拖久了会漂）
- `frontend/src/Capture.svelte`：三态（取景 / 框选 / 成品）；旋转把 90° 烘进**无损帧**（整数矩阵 + 关平滑，逐像素置换无重采样），选框跟着内容转
- 确认链路：裁无损帧 → PNG base64 → `capture.Rectify` → `capture.Card` → `library.Add`（顺序在 dfc337e 调整过，为的是可重入）

**已在真机上跑通**：设备私有目录里出现了 `cards/<sha256>.png`（65,825 B）与 `library.db`，查库得到 2 道错题 —— 整条链路端到端执行过。

**仍未验证**：真机上只冒烟跑通过一次；成品卡片图分辨率首次实测 249×172 px（用户判断可接受，已加 `getUserMedia` 分辨率约束但未复测）。

**已知与 ADR-0006 的不一致**：选框是轴对齐矩形（用户明确决定），所以这上面的 `Rectify` 是几何恒等变换，梯形畸变原样保留。ADR-0006 已于 2026-09-16 更正说明，四角独立拖是预留而非当前能力。
