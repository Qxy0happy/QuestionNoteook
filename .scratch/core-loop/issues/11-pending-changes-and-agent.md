# 11: 待批准层 + Agent 管理数据

**What to build:** 应用内有一个能读写数据的 agent。它**读得到一切**，但每一次写都先生成一条**待批准改动**，用户逐条批准或丢弃；批准前不影响正式数据。

**Blocked by:** 09（VLM 客户端）、10（讨论）

**Status:** ready-for-human —— Go 侧测试全过（含安全属性那七把锁）；界面接线完成、`svelte-check` 0 错；**真机与真实网络都未验**

- [x] agent 能回答全局问题（如「我数学哪块最弱」），靠读数据
- [x] agent 的每一次写都生成一条待批准记录
- [x] 有一条测试断言**不存在绕过待批准层直接改数据的路径** —— 这是安全属性，不是功能
- [x] 逐条批准、逐条丢弃都可用
- [x] 丢弃一条不影响其他已批准的改动
- [x] 界面上能看到待批准改动的清单与数量

## Comments

### 用户定的两条方向

1. **agent 靠「工具调用循环」读数据** —— 把「查错题 / 查标签 / 查复习记录」做成工具交给模型，它自己决定查什么，从而回答「我数学哪块最弱」这类没写死的问题。
2. **第一版只允许提议「标签」**（建/改/删标签节点、给错题挂标签）。复习状态、删错题都不做。

### 那条安全属性是怎么证的（本票的核心）

**第一步：让「绕过」在类型上不存在，而不是靠纪律。**

- 读的那一侧手里是 `agent/store.Querier` —— 一个**只有 `Query` 和 `QueryRow`** 的接口，不是 `*sql.DB`。读路径不能写，不是因为它忍着不写，而是它**手上没有任何一个能调的写方法**。
- `agent` 这个包**import 不到**执行者那两层（`agent/store`、`agent/apply` 是独立包），也 import 不到 `internal/library`。
- `agent.Service` 的字段里没有一样是 `Applier`。全应用只有一个东西持有执行者：`agent.Pending`。
- **唯一一条从「提议」走到「执行」的路**是 `Pending.Approve(id)`：它先从 `pending_changes` 表里读回那一行，再拿它去 `Apply`。所以执行者能吃到的每一条改动，**都必须先在待批准表里躺过一行**。
- 库那一层再拦一道：迁移 5 的 `action` 上有 `CHECK (action IN (...))`，别的种类的改动**根本存不进来**。

**第二步：用反射与源码扫描把这些性质钉成会红的测试**（`internal/agent/safety_test.go`，七把锁）。
白名单是常量，接口与具体类型的方法集必须**恰好等于**白名单（多一个方法就红）。

**第三步（这一步才是关键）：造两次故意的违规，看锁是不是真的会响。**

- 实验 1：给读路径加一个 `w *sql.DB` 字段 + 一个直接 `DELETE FROM questions` 的方法 → 四把锁同时响。
- 实验 2：在 `Pending.Propose` 里偷偷加一行 `p.applier.Apply(c)`（这正是「绕过待批准层」最像的那一种）→ 行为锁立刻红，而且输出的是**行级可读差异**（哪张表变了、变了哪一行）。
  两次实验都已完整还原（全树 `TEMP-EXPERIMENT` 命中 0 处）。

**第四步：修掉一个会让整组锁失效的 bug。** `isDatabaseSQL` / `isOurs` 一开始直接读 `t.PkgPath()`，
而**指针类型的 `PkgPath()` 是空串** —— 后果是 `*sql.DB` 对遍历完全不可见（实验 1 那种字段当时**会通过**），
而且 `*agent.Service` 上的方法集压根没被检查过。修法是先剥指针。这是自己抓出来的，值得记一笔：
**一组看着很严的锁，可能整体是空转的。**

### 接口按「用得上什么」定，不按「谁现成」

`ReadStore` 收的是 `questionReader`（只有 `ListQuestions`）和 `tagReader`（只有两个读方法），
不是 `*library.Store` / `*tags.Service` —— 后者各自带着三个以上的写方法，递过去等于**为了用一个读方法
把写动作也一起递过去**。同理 `Provider` 接口在 agent 那条路上只声明了 `Chat`（那条路上一张图都没有，
就不该拿着 `Upload`）。

### 三个自己定的上限（都在票的验收项之外，但不定不行）

- **回合上限 8**。用尽之后**不是报错**，而是把工具收走再问最后一次，让它拿现有信息作答并说明哪里不确定；
  已经提议出来的改动**一条都不丢**。
- **每条提问最多提议 20 条**。撞上时返回给模型一句工具错误让它停下 —— 让它停下比让它继续有用。
- **全局提问扫多少数据：不是靠拒绝读，而是靠限制进上下文的东西**。`list_questions` / `review_history`
  分页（默认 50、上限 200）；`review_stats` 在 SQL 里聚合、按题去重再沿标签树向上摊，所以
  「我数学哪块最弱」**一次调用就够，而且响应大小由标签数封顶、不由题目数封顶**。
  （顺带修掉一个真实的聚合 bug：一道题在它路径的每一层都挂了标签时会被重复计数。）

### 迁移 5：`pending_changes`

**为什么落库**：这一层是用户的**收件箱**。重启之后「agent 提议过什么」要是没了，用户就再也看不到
那些改动 —— 而他并没有拒绝过它们；界面上那个「待批准 N 条」也会自己归零。批准是一个**人的决定**，
决定得有对象，对象得活过这一进程。

`payload` 存 JSON 文本而不是拆成一堆列：不同 action 要的字段不一样，拆列会长出一片「这条改动用不上」
的空列，而它本来就是**模型说的那句话**。`problem` 与 `status` 分开，是为了让「批准失败」不会把一条
改动标成已生效（状态仍是 pending —— 那一步确实没发生）。

### 一处原先的绕法已被撤掉

这条迁移**一度**带 `IF NOT EXISTS`，那是为了绕开「三个测试里手抄的 DROP 清单漏了它」。
绕法是错的：`IF NOT EXISTS` 是真的弱化（「表在、但列不对」时静默放过，而那恰恰是迁移最该拦住的坏库）。
现在表清单由 `migration.tables` 汇总（见 `library.TablesIntroducedAfter`），测试不必手抄，
所以没有绕的理由了 —— 迁移 5 与前面四条一样是裸的 `CREATE TABLE`。

### 交付时会看到的多余面

- `Pending.Propose(Change)` 是导出的，会出现在生成的 `pending.ts` 里。它**动不了正式数据**
  （最远只写 `pending_changes`），所以不构成绕过；但它是多出来的面。
- 反射只看得到**导出**方法：包内一个未导出的赋值方法对反射不可见，由源码扫描那几把锁覆盖。
- 锁钉的是**类型**不是**实例个数**：没有任何测试禁止有人造出第二个 `PendingStore`（那需要手里有
  `*sql.DB`，而全应用只有 `main.go` 持有它）。「只有一条写路径」在实例层面的保证来自
  `main.go` 里 `apply.New` **只被调用一次**。

### 接线（本次补的）

- `main.go`：`apply.New(tagsService)` 只构造一次 → `agent.NewPending(...)` → 同一个对象既当
  `agent.Service` 的提议出口，也自己绑给前端。**配置文件与 VLM 用的是同一份 `vlm.json`** ——
  agent 也要模型，而模型名只能从配置来（ADR-0005）。
- `Agent.svelte`：加了「问一句」（回答用 `Markdown.svelte` 渲染，与讨论那边同一套）与
  `<Pending />`（待批准清单）。`Pending.svelte` 的 `refreshKey` 在每次提问后 +1，让清单当场重读。

### 未验证

- **真机没跑过**；真实模型一次都没调过（一律走 `vlm.Fake`）。提示词与工具描述都是暂定的。
- `Pending.svelte` 只做过类型检查（对着真实 bindings），**从没渲染过**。
- 「批准一条会真的改到标签树」这条链在服务层测过，但**没有端到端**跑过。
