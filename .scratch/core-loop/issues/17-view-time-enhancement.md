# 17: 查看时的图像增强（去阴影），以及梯形矫正该待在哪儿

**What to build:** 用户原话：「我需要查看时进行增强，以及梯形矫正，以避免阴影等的影响。这个应该可以在 100ms 内实现吧？」

拆成两半 —— 它们在技术上**不属于同一层**，混在一起想会得出错的方案。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human —— 已实现（`frontend/src/enhance.ts` + 详情页的开关）；**手机上一次都没跑过**

- [x] 查看题图时能一键增强（去阴影 / 提对比），**不写回库里**
- [x] 增强的开关在详情页（与「看答案图」同一排），默认关：原图是基准，增强是看法
- [x] 大图上不卡（桌面 136 万像素 12.4ms；而且按**显示尺寸**算，手机上只需 1.6ms 那一档）
- [ ] 真机上读一次那个毫秒数 —— 按钮旁边直接显示，不用改代码

## 实现（2026-09-16）

**算法**：平场校正，`反射率 = 原图 / 光照`，光照 = 大半径模糊。
参数：`downscale 8`（块平均，顺带低通掉纸纹）、`radiusRatio 0.12×小图短边`、
`paper 232`（**不取 255**：光照总有百分之几误差，定在 255 就把纸纹一路削平）、
`maxGain 3.2`（比纸面暗 3.3 倍以上的地方只做部分校正 —— 暗处除以接近 0 的数会炸出白噪声）。
逐像素那一趟走 256×256 的 LUT，内层循环里没有除法、没有夹取、没有分配。

**两处是量出来才改对的，值得记下来：**

1. **光照估计必须先「取局部最大」（膨胀）再模糊，不能直接用局部平均。** 字会把平均值拉低，
   而它是**分母** —— 有字的地方分母偏小就被多提亮。实测（合成图 2903×470、正文覆盖率 10%）：
   局部平均那一版**把 87% 的纸面顶到 255 削平**，纸纹一丝不剩；加膨胀后削顶 **0%**
   （纸面 sd 33.7 → 6.5）。道理是「墨总比纸暗，这一带最亮的东西才是纸有多亮」。
2. **双线性放大拆成两段做。** 横向插值的结果与 y 无关，先算一次给下面几行共用，输出行那一趟
   只剩纵向一插。实测把整条链从 **33.4ms 降到 12.1ms**（瓶颈原本在放大，不在逐像素）。

**实测**（Node v26.8.1 / Ryzen 9 7940H / 合成图，只量算法那一趟）：

| 场景 | 尺寸 | 像素 | 中位 |
|---|---|---|---|
| 真实题图尺寸 | 2903×470 | 1,364,410 | **12.4 ms** |
| 手机详情页实际工作尺寸 | 1008×163 | 164,400 | **1.6 ms** |
| 竖幅手机照片 | 1280×2800 | 3,584,000 | 33.3 ms |

约 9ms/MPx，线性很好 → **136 万像素用掉 100ms 预算的八分之一，WebGL 没有必要**（只在桌面 CPU 上成立）。

**去阴影效果**（按真值把纸面与墨迹分开统计）：纸面 164±33.6 → **228±6.6、削顶 0.00%**；
墨/纸对比在八个阴影深浅桶里**全部收敛到 0.100**（= 真的墨反射率 10%）。

**几个取舍**：按**显示尺寸**算而不按原图算（手机 1.6ms vs 12.4ms，代价是那张增强图只有显示所需
的像素 —— 而它是 `object-fit: contain` 且没有缩放交互，看不出来）；`paper=232` 换来不削顶
（宁可灰一点，别丢纸纹与浅灰铅笔字迹）；`maxGain` 换来暗处不出麻子；结果按题缓存在两个槽位里；
**不做 resize 重算**（拖一次窗口会触发几十下 ResizeObserver）。

**关掉是真的回到原图**：`<img>` 的 `src` 换回原图那个 data URL —— 同一份 PNG 字节、同一个原生
解码器，所以是逐像素一致，不是「反过来再算一遍」。

**按钮旁边显示这一趟量到的毫秒数**（点下去到能显示的整段，含解码/画布/编码）。这是为了让
真机那个数**不用改代码、不用开控制台就能读出来** —— 票里说这一格不能靠推。

## Comments

### 复习页也要这个开关（2026-09-16 用户提的），于是把那条链抽了出来

**状态：**已部署并核过（设备上那份 APK 与本地构建逐位相同；这条链的「构建 → 嵌入 → 装机」三步各自有证据）。**真机未验** —— 这个开关在手机上还没被按过。

用户原话：「复习的界面也要增强的按钮，这个应该可以做。」

实现里有一批**抄一份就会走样、而且走样了不报错**的规矩：按显示尺寸算（省时间的全部来源）、
放大之后换一版按原图算的、异步回来对不上号就丢掉、旧的那张要在 DOM 换过 src **之后**才 revoke。
所以整块抽成了 `frontend/src/enhanced.svelte.ts`（`EnhancedShots` 类，一个实例管题图 + 答案图
两个槽位），两页共用同一份 —— 与票 07 里「不重写一棵树、复用 TagFilter」同一条理由。
算法本体仍在 `enhance.ts`（不碰 DOM、不碰 canvas，能脱离浏览器单独量）。

两页只剩接线：告诉它「这一槽现在显示的是哪张图、按哪块尺寸算」（`refreshShots`）。

**有一处行为有意不同**：题库详情里开关**每换一道题就重置**（原图是基准，增强是这一次临时
打开的看法），复习页则**整段复习一直开着** —— 复习是一口气做十几道，每题都要重新按一下会很烦。
图片本身仍然按题重算，所以不存在「拿了上一道的增强图」。模块里两个入口把这件事写成名字：
`resetForNewQuestion()` 与 `resetKeepingEnabled()`。

### 实测：Go 里做到达不到 100ms（2026-09-16，用真实题图量的）

在 4 张真实题图（2903×470，约 136 万像素）上跑了一遍「平场校正」式的去阴影
（按大半径均值模糊估光照，逐通道除掉它；可分离滑动窗口，O(N)），**桌面 CPU**：

| 半径 | 增强 | PNG 解码 |
|---|---|---|
| 2% 像素宽 | 中位 68ms / 最慢 101ms | 中位 91ms / 最慢 112ms |
| 8% 像素宽 | 中位 70ms / 最慢 104ms | 中位 99ms / 最慢 109ms |

**光解码就把 100ms 的预算吃掉了**，还没算编码回传。手机 CPU 只会更慢。半径的影响很小
（滑动窗口是 O(N) 的，半径不改变复杂度）—— 也就是说**瓶颈在解码，不在算法**。

### 所以：增强放前端做

这条链上解码那一半**本来就不必由 Go 做**：`QuestionImage` 回的是图片的**原样字节**的 base64
（Go 不解码），浏览器解 PNG 是**原生**实现，快得多；而像素活可以放 GPU。
所以结论不是「达不到」，是「不该在 Go 里做」。

做法（实现者可以改，但要说清为什么）：
- 图片已经是 base64 data URL → `Image` → canvas。解码由 WebView 原生做。
- 去阴影：先在小尺寸上估光照（缩到 1/8 做模糊，再放大），然后逐像素除 —— 小图上的模糊是
  免费的，逐像素那一趟在 TypedArray 上是线性的。
- 如果 JS 那一趟也不够快（手机上要实测），再上 WebGL 片元着色器 —— 这正是**必须在真机上看**
  那一格（见下）。
- **不写回库里**：spec 的 Out of Scope 写着「不做不可逆增强」，而 ADR-0007 说原图处理完就丢了 ——
  所以增强只能是一种**看法**，不能覆盖题图本身。这也意味着它随时可以关掉回到原样。

### 梯形矫正属于**拍摄时**，不是查看时

用户把它和增强放在一起说，但前提不同：**它需要界外的像素**。裁切已经把界外丢掉了 ——
如果纸边被切掉，在裁后的图上**根本找不到那四个角**。所以查看时做只能对「恰好裁得够宽」的图
做二次变形，是有损的补丁。

它该待的地方是采集：那正是 ADR-0006 预留的「四角独立拖」——
`capture.Rectify(quad)` **本来就吃任意四边形**（今天传的是恒等四角，见 `Capture.svelte` 的
`confirm`），而且它是 Go 侧**唯一被 fixture 测试覆盖的入口**。前端要做的只是把那四个值换成
各自的拖动结果，**Go 侧一行都不用改**。

⚠️ 注意 ADR-0006 同时明确「**不做边缘检测**」（手工框，不猜）—— 所以四角也是手拖，不要顺手
加一个自动找纸边的功能。要加那是另一张票、另一个决定。

### 未验证

- 上面那张表是**桌面 CPU** 上的数，手机上的绝对数字没量过。前端的做法到底多少毫秒
  （以及要不要上 WebGL）**必须在真机上测**，这一格不能靠推。
- 去阴影的**观感**（会不会把浅色字迹也一起吃掉、纸面纹理会不会被放大）没在真机上看过；
  那是个美学判断，得用户定。
- 四角拖动的手感、以及它和现有选框（`CropBox`）的关系（是同一个交互加四个角，还是另一种模式）
  都没设计过。
