# 18: 复习参数设置（间隔模糊 + 考试日期）

**What to build:** 设置页多一个「复习参数」细分项：一个间隔模糊的开关、一个考试日期。填了考试日期之后，任何评级算出的间隔都不会超过「距考试还有几天」；保存时把库里已经排到上限之外的到期日拉回来，并告诉用户拉了几道。

**Blocked by:** 08（复习：今日队列 + 四档评级 + FSRS）

**Status:** ready-for-agent

- [ ] 设置页能开/关间隔模糊，能填/清考试日期
- [ ] 填了考试日期后，四档间隔都不超过「距考试还有几天」（新卡与复习过的卡都是）
- [ ] 这个上限**每天重算**：过了一天，上限跟着小一天（不是启动时烘死的）
- [ ] 考试日期为空、或已经过去：退回官方默认上限，且界面说清「这个上限当前不生效」
- [ ] 保存时把到期日超出上限的题拉回上限内，返回拉了几道
- [ ] 拉回来只动 `due_at`；`stability` / `difficulty` / `scheduled_days` 一个都不动
- [ ] 设置文件坏了（不是 JSON / 日期解析不了）不让复习瘫掉：用默认值继续跑，把问题显示在设置页
- [ ] Go 侧测试覆盖上面每一条；`params_test.go` 那条「与官方默认只差一处」的断言跟着改成「差哪几处，取决于设置」

## Comments

### 决定（2026-09-16，用户答的）

用户原话：「间隔时间太长了。现在还剩 94 天」，接着提议「要不加个能够手动调整参数的设置细分项」。

三个问题问下来他选的是：

1. **暴露哪几项**：只选「间隔模糊」与「考试日期」。**没有**选期望保留率、也没有选最大间隔天数。
2. **默认值**：只加界面，默认不动（模糊关着、考试日期为空）。
3. **库里已排出去的到期日**：保存时拉回来。

第 1 条的省略不是遗漏 —— 有了考试日期当硬边界，保留率与手填上限都是多余的旋钮（理由写在 ADR-0008 里）。所以本票**不做**「期望保留率」和「最大间隔天数」两个字段，别顺手加上。

第 2 条意味着：这个功能装上之后**间隔还是长的**，直到用户自己把考试日期填进去。所以界面得把这件事说清楚 —— 「填上考试日期，间隔就会被压到那天之内」，而不是让他对着一堆没变化的数字猜。

### 上限怎么算

```
上限 = 考试日期（本地日） - 今天（本地日），单位天
```

用**本地日**相减，不是拿两个时刻相除 —— 「还剩 94 天」= 本地 9/16 到本地 12/19 差 94 个日历天，与今天几点钟无关。`Service.now()` 在生产里是 `devtz.Now()`（设备时区），所以 `now.Date()` 拿到的就是用户日历上的日期。

边界：
- 考试日期**就是今天** → 上限 1 天（不是 0：0 会被 FSRS 的校验挡下，而且「今天考试」也还是得排到明天之前，1 是最小的合法值）。
- 考试日期**已经过去** → 上限**不生效**，退回官方默认 36500。这是有意的：不这么办的话上限会变成负数，被夹到 1 之后**每一道题每天都到期**，队列直接爆掉 —— 那比「上限不管用」糟得多。
- 上限**每次算调度参数时现推**，不在服务构造时算好存起来。存起来的话过了午夜它就旧一天，而复习恰恰是每天早上的事。

### 拉回来动哪一列

只动 `review_states.due_at`：

```sql
UPDATE review_states SET due_at = ? WHERE due_at > ?
```

`stability` 与 `difficulty` **一个都不动**。理由：那两列是「这个人对这道题记得多牢」的估计，是 FSRS 从他的评级史里学出来的；为了配合一个新的上限去改它们，等于伪造他过去的表现，而且下次评级的起点就错了。而改 `due_at` 只是「提前复习」—— 那是 FSRS 允许的用法（提前复习稳定度涨得少一点，仅此而已），不是把算法骗过去。

`scheduled_days` 也不动（它是「上一次排出去时算的是多少天」，是历史）。

拉回来的天数取上限本身，也就是落在那一天到期。「不能晚于考试」是本票唯一要保证的事。

### 与票 08 的关系

票 08 里那句「权重没动，也没改 RequestRetention / MaximumInterval」现在**只在没填考试日期时成立**。`params_test.go` 那条「与官方默认只差一处」的断言改成参数化：传默认设置进去仍然是差一处（就是关掉的学习步）；传一个填了考试日期的设置进去，就多差一处 `MaximumInterval`，而且值等于距考试的天数。

那条测试防的是「库升级后默认值悄悄变了」这一类**静默**的坏，改参数化不能把这一点丢掉 —— 所以它比的仍然是 `fsrs.DefaultParam()`，不是我们自己写的常量表。

### 实现中量出来的两件事（2026-09-16）

**一、官方库的 `MaximumInterval` 是软的，这条得我们自己收口。**

写第一条断言时它红了，报的是「复习过三次的卡 Good 是 95 天 —— 应当落进 1..94」。那不是测试写错，是库的行为：它先把每一档夹到上限，再为了保住四档的严格次序往上加，于是

```
上限 94 天：Hard 94 / Good 95 / Easy 96
```

上限**能超出两天**。而这一票要的正是「任何评级都不会排到上限之外」—— 超出两天就是考后两天。所以加了一处 `clampToCap`，收在评级的最后一步；**预览走同一个收口**，否则界面写着 95 天而真去做是 94 天。

收的只是 `Due` 与 `ScheduledDays`；`stability` / `difficulty` 仍是库算的原值（与「拉回来只动 due_at」同一个理由）。这条现在由 `TestPreviewRespectsTheCap` 与 `TestSetConfigPullsBackDistantDueDates` 一起钉着。

**二、「拉回来」的界线是**当时**的倒计时，不是保存那一刻的。**

`TestSetConfigPullsBackDistantDueDates` 里那道题是一路评 Easy 推到远期去的，推到时钟走到了 11/29 —— 于是填上考试日期（12/19）时生效上限是 **20 天**，不是 base 那天的 94 天。我第一版把期望值写死成 94，于是它红了；错的是测试的期望，不是实现：上限本来就该按**此刻**重算（这也正是「不烘进调度器」那条验收项要的）。现在那两条断言（`DaysToExam == 20`、被拉到「最后复习那一刻 + 20 天」）一起把这件事钉住了。

### 界面上的两个决定

- **预览跟着表单走，不等保存**。所以 Go 侧多了一个 `Preview(c Config)`：它按传进来的设置算一遍视图，**不落盘、不动库、不改缓存**。不加它的话，用户想看「把考试日期改成 12/19 会怎样」就得先真存一次 —— 而那一次会顺手拉一批到期日回来。日期打了一半（`2026-1`）时它返回错误，前端**静默**退回按已保存那份显示，不弹红字：他还在打字。
- **四档的名字抽成了 `frontend/src/ratings.ts`**。设置页要写「Again 1 天 · Hard 2 天…」，复习页那四个自评按钮也写着同一组名字。抄两份的话，改一处就会有另一处开始说谎。
