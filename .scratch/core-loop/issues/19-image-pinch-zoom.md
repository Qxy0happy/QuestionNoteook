# 19: 查看题图时的就地放大（捏合 + 拖动）

**What to build:** 在题库详情与复习页，题图/答案图上双指捏合能放大、放大之后单指能拖着看，捏回比 1 倍还小就归位。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human —— 手势数学在 Node 里量过（10 条全过）；**真机上一次都没试**

- [x] 题库详情的题图与答案图能捏合放大、放大后单指拖动
- [x] 复习页的题图与答案图同上
- [x] 没放大时单指一概不接管：上下滚列表、左右翻页照旧
- [x] 放大时溢出不外溢（不盖住相邻元素、不把外层滚动条撑出来）
- [x] 换一道题就回到「铺满看全」
- [x] 捏到比 1 倍小、抬手归位（这是「缩回原样」唯一的路，所以不存在卡在放大态出不来）
- [x] 放大之后，增强（去阴影）那一版按**原图**重算一次，不是把屏幕那么大的一版拉大
- [ ] 真机：上面每一条（尤其手势仲裁那两条）

## 决定（2026-09-16，用户答的）

用户原话：「我想要的是查看题目图片时的放大功能，最好是能够手势放大。」三个问题问下来：

1. **形态**：**就地放大**（不是全屏查看器，也不是两个都要）。
2. **手势**：**双指捏合** + **单指拖动平移**。没有双击放大，也没有倍率按钮。
3. **范围**：**题库详情** + **复习页**（各两处：题图与答案图）。

第 2 条意味着**没有倍率按钮**，所以「缩回原样」只能靠手：捏到 1 倍以下、抬手归位。这是有意
留的唯一退路，实现里写成硬规矩（`MIN_SCALE` 0.6 → 抬手回 `FIT`）。

## 手势仲裁是这件事真正难的地方

三条规矩，写在 `frontend/src/zoom.ts` 的文件头：

1. **两根手指才算捏合**，一发现两指就 `preventDefault` —— 页面既不滚也不翻页。
2. **放大之后单指拖动是平移**，同样 `preventDefault`（不然会一边平移一边把页翻走）。
3. **没放大时单指一概不碰。** 那一根手指还要能上下滚列表、左右翻页。

第 3 条决定了**不能**用 `touch-action: none` 一了百了 —— 那会把整页的滚动一起掐掉。
只能在 `touchmove` 里按情况 `preventDefault`，所以那个监听必须是 **non-passive** 的
（`touchstart`/`touchend` 仍然是 passive：那两处不拦任何东西）。

**页面级的缩放要先关掉**，否则它跟我们的手势抢同一个动作，而且它缩的是导航栏和列表：

- `frontend/index.html` 的 viewport 加上 `maximum-scale=1, user-scalable=no`；
- `MainActivity` 里 `setSupportZoom(false)` + `setBuiltInZoomControls(false)`。

两处都得有：viewport 管「页面的意愿」，那两行管「WebView 的能力」。只有一处生效时行为随
WebView 版本而变 —— 所以不赌，两个都写。

## 数学：先在 Node 里量，再上真机

手势的数学错了**不会报错**，只会让图在手指底下乱跳 —— 那种错只能对着数字看。而这些是纯函数
（`clampZoom` / `pinchTo` / `panBy` 只吃状态与几何，不碰 DOM），所以不必要真机。

量法：`tmp/zoomprobe/probe.mts`（未进版本库，与当初 tmp/bench 一样），`node tmp/zoomprobe/probe.mts`。
舞台 360×200、图 300×150 居中，10 条：

```
ok   夹取不改变原样: translate(0px, 0px) scale(1.0000)
ok   捏合 x1.2: 不动点落在 (280.0, 150.0)，手指在 (280, 150)
ok   捏合 x2:   不动点落在 (280.0, 150.0)，手指在 (280, 150)
ok   捏合 x4:   不动点落在 (280.0, 150.0)，手指在 (280, 150)
ok   捏合 x0.5: 不动点落在 (280.0, 150.0)，手指在 (280, 150)
ok   两指整体平移 40,20 → 图移动 40,20
ok   拖到右下边界: translate(-30px, -25px) scale(2.0000)
ok   拖到左上边界: translate(-270px, -125px) scale(2.0000)
ok   放大 2.5 倍后缩回 1 倍: translate(0px, 0px) scale(1.0000)
ok   猛拉一把：倍率停在 4（上限 4）
```

两条最要紧的：

- **「原样」是不动点。** 夹取在 scale=1 时必须原样吐回来，否则每次抬手都会把图挪一下 —— 一
  个看得见的跳。这条靠「容器量 padding box、图片位置从自身的框反推」实现，见 `measure()`。
- **手指底下那个点在图片上的位置一动不动。** 捏合的不动点取的是**手势开始时**两指中点落在
  图片上的那个点（不是每帧重算），所以两指整体移动时图会跟着走 —— 那才是真实捏合的手感；
  而「捏哪里放大哪里」也因此在同一行代码里成立。

拖到边界的两个数也值得看：x = -30 正好是「图片左上角贴住容器左上角」（未缩放时图片离容器
左边 30，那 30 就是 300 与 360 的一半差），再往右拖不会有缝。

## 放大之后增强图要重算一次

票据 17 的增强是**按显示尺寸**算的（那是它省时间的全部来源：手机上 1.6ms 那一档）。放大两三倍
之后，那一版只有屏幕那么大，看到的全是插值的糊 —— 而「看得清」正是用户放大要的东西。

所以倍率一过 1.05 就把那一版换成按**原图**算的（`boxFor` 传原图的 naturalWidth/Height，1:1），
每个槽位只换一次、换过不降级（缩回去看只会更清楚）。上限仍然由 `MAX_PIXELS` 兜着。

代价是按下捏合之后可能有一小段等待（题图 136 万像素，桌面 12ms 那一档；手机上没量过），
那期间显示的是原来那一版而不是空白 —— 与「增强没算好时显示原图」同一个做法。

## 未验证

- **手势仲裁那两条**（两指能不能抢过外层翻页、放大后单指拖动会不会顺带翻页）。纸上推不出来：
  这台设备上 WebView 的版本、翻页容器用的是 scroll-snap 还是 transform，都会影响。所以这里的
  失败方式有意做软：抢不到就退化成「没放大」，而 `touchcancel` 一律把手势收拾干净，不会卡住。
- 真机上的手感（倍率上限算得对不对、捏合的跟手程度）。倍率上限 = 原图像素 ÷ 显示设备像素，
  夹在 2..6 之间 —— 这个算式只在真机上才知道好不好用。
- 页面级缩放松掉之后，**有没有别的地方依赖它**（比如讨论页里用户想放大整页的字）。目前想到的
  没有，但那是一句「想」，不是一次检查。
